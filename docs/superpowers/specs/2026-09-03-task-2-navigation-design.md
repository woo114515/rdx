# 任务二：固定航点巡逻与动态避障设计

## 目标与已确认需求

任务二在固定实体场地中运行。场地已搭建，但尚未生成 ROS 二维地图。
起点与终点为同一位置，另有三个固定任务点，现场均用黑色胶带标记。
机器人每次可以按固定位置和朝向放置，运行顺序固定为：

```text
起点 -> 任务点 1 -> 任务点 2 -> 任务点 3 -> 起点/终点
```

到达中间任务点后无需停留或执行额外动作。场地包含固定障碍物，巡逻途中还会
随机出现临时障碍，包括移动人员的腿。赛事没有规定最高速度或最小安全距离，
因此这些值必须作为 YAML 参数保守设置并通过实测调整。

黑色胶带不作为运行时感知输入。二维激光雷达通常不能可靠区分地面胶带；建图
完成后，在 RViz 地图中记录起点和三个任务点的 `map` 坐标及朝向。

## 技术路线

采用“单次建图、固定地图定位、Nav2 导航”的路线：

1. 使用 MS200P 和 SLAM Toolbox 人工遥控建立场地地图并保存；
2. 正式运行时加载静态地图，以 AMCL 完成定位；
3. 使用 Nav2 的 NavFn 全局规划器和 DWB 局部控制器；
4. 任务节点按固定顺序发送四个导航目标；
5. `/scan` 同时更新局部和全局代价地图，处理临时障碍；
6. 独立安全仲裁节点是底盘速度命令的唯一出口。

如果 SLAM Toolbox 在实车采图中无法稳定闭环，可回退到厂商已经接入 MS200P 的
GMapping 启动链。两者均只在建图阶段使用；正式巡逻不边走边改写长期地图，避免
把人员等动态物体固化为地图重影。

D-Robotics 当前文档确认 RDK X5、Ubuntu 22.04/Humble 支持 SLAM Toolbox 和
Navigation2，TogetheROS.Bot 与标准 ROS 2 接口兼容：

- [TogetheROS.Bot 简介](https://developer.d-robotics.cc/tros_doc/tros)
- [SLAM 建图](https://developer.d-robotics.cc/tros_doc/apps/slam)
- [Navigation2](https://developer.d-robotics.cc/tros_doc/apps/navigation2)
- [使用 ROS2 package](https://developer.d-robotics.cc/tros_doc/quick_start/ros_pkg)

官方示例使用 TurtleBot3/Gazebo，只证明框架可在 RDK 上运行。ROSMASTER X3 的
轮廓、麦克纳姆运动学、MS200P、底盘接口和安全行为仍需本项目单独配置。

## 组件与数据流

```text
MS200P /scan -------------------> SLAM Toolbox（仅建图）
       |                         AMCL + Nav2 costmaps（正式运行）
       |
底盘 /odom_raw -> EKF /odom + TF -> 定位与规划

固定航点任务节点 -> NavigateToPose -> Nav2 /cmd_vel_nav
                                         |
                                         v
                              安全仲裁（超时/限速/停车）
                                         |
                                         v
                                      /cmd_vel
                                         |
                                         v
                                  厂商底盘驱动
```

计划拆分为以下本项目 ROS 包：

| 包 | 责任 |
| --- | --- |
| `rdx_bringup` | 最小化启动底盘状态、雷达、机器人描述和 TF；不包含意外控制源 |
| `rdx_safety` | 速度输入超时、限速、传感器失效和退出归零 |
| `rdx_navigation` | 地图、AMCL、Nav2、DWB 和代价地图参数 |
| `rdx_mission` | 固定航点配置、顺序执行、失败和完成状态 |

## 厂商软件复用边界

小车已经安装以下版本，无需在当前系统上重复安装或立即升级：

- `ros-humble-navigation2` 1.1.16；
- `ros-humble-nav2-bringup` 1.1.16；
- `ros-humble-slam-toolbox` 2.6.8。

厂商 `yahboomcar_nav` 已包含 DWB、TEB、GMapping、地图保存和示例地图。第一版
复制其 `dwb_nav_params.yaml` 到本项目作为可追溯基线，不直接修改
`/home/sunrise/yahboomcar_ws`。

下列项目必须在落地运动前修正，不能以“保留原配参数”为由跳过：

- 实车各节点统一 `use_sim_time: false`；厂商参数中 `bt_navigator` 为 `true`；
- Nav2 输出改为 `/cmd_vel_nav`，不得直接进入厂商 `/cmd_vel`；
- 使用包含固定前叉的实测 footprint，不能沿用 `robot_radius: 0.1`；
- 降低原配 `0.26 m/s` 线速度和 `1.0 rad/s` 角速度；
- 增大原配 `0.12-0.2 m` 障碍膨胀范围，并单独设置人员减速/停车区；
- 首轮禁用未经验证的自动旋转和倒车恢复；
- 导航失败不得因 `stop_on_failure: false` 静默跳过任务点；
- TF、雷达或速度请求陈旧时，安全仲裁应在不超过 0.3 秒的目标时间内归零，
  并持续发送零速度直至恢复条件满足。

首轮巡航目标速度为 `0.15-0.20 m/s`，人员减速区从约 `0.5 m` 起步调试；最终
阈值以真实 footprint、雷达盲区、地面制动距离和现场测试结果为准。

## 上午实机验证结果

### 环境与设备

- ROS 运行使用 `ROS_DOMAIN_ID=99`；
- `/dev/oradar -> /dev/ttyACM0`；
- `/dev/myserial` 曾先后指向 `ttyUSB0` 和 `ttyUSB1`，代码必须使用稳定别名；
- 根分区 27 GiB，约使用 87%，剩余约 3.4 GiB；
- 厂商完整 bringup 会同时启动底盘、EKF、手柄和机器人描述，不适合发现阶段。

### 雷达与静态 SLAM 冒烟测试

测试时先停止键盘和厂商完整 bringup。底盘驱动的输入被重映射为
`/cmd_vel_disabled`，ROS 图中不存在 `/cmd_vel`，因此测试没有运动出口。

实测结果：

- MS200P 成功打开 230400 波特率串口；
- `/scan` 类型为 `sensor_msgs/msg/LaserScan`，频率约 9.9 Hz；
- 帧名为 `lidar_link`，接近 360 度，每帧约 450 个测距点；
- 配置量程为 0.15-20 m；
- `/odom_raw` 频率约 10 Hz；
- `odom -> base_footprint -> lidar_link` TF 可查询；
- SLAM Toolbox 成功注册雷达并发布 `/map` 与 `map -> odom`；
- 静止地图分辨率为 0.05 m，尺寸为 337 x 154，共 51,898 个栅格。

这证明“MS200P -> 里程计/TF -> SLAM Toolbox -> OccupancyGrid”链路可用。
机器人没有移动，因此结果只是周围环境的局部快照，不代表完整场地图质量。

测试结束后所有 SLAM、TF、底盘状态和雷达进程均已停止，两个串口无残留占用。
MS200P 厂商节点在 `Ctrl+C` 时触发用户态 `buffer overflow` 并以 `-6` 退出；它
没有造成内核崩溃，但需要在本项目 launch 的关闭和重启策略中记录并验证。

### 已发现的运动风险

上午曾在小车主目录发现 `drive_one_meter.py`、`drive_figure_eight.py` 和后续
键盘程序，它们不在 Git 仓库中，并直接发布 `/cmd_vel`。至少两个自动运动脚本
在 TF 丢失时仅返回等待，不立即停车。厂商 `Mcnamu_driver` 没有命令超时，因而
任何直接发布速度的临时脚本都不得用于后续落地建图。

## 建图与正式运行流程

### 建图阶段

1. 清理重复 ROS 节点和所有直接 `/cmd_vel` 发布者；
2. 启动最小底盘状态链、机器人描述和 MS200P；
3. 验证 `/scan`、`/odom_raw`、融合后的 `/odom`、TF 和零速度状态；
4. 启动 SLAM Toolbox 和开发机 RViz2；
5. 遥控输入进入 `/cmd_vel_teleop`，通过安全仲裁后再到 `/cmd_vel`；
6. 低速沿场地边界和主要通道行驶，多做闭环并避免把人员写入地图；
7. 保存地图，重新加载并验证墙体无明显重影、通道连续；
8. 在 RViz 中记录起点、任务点 1/2/3 的位姿。

### 正式运行阶段

1. 按固定位置和朝向放置机器人；
2. 加载静态地图，设置或自动发布初始位姿；
3. 确认 AMCL 收敛、雷达与地图对齐；
4. 任务节点按顺序发送四个 `NavigateToPose` 目标；
5. 局部代价地图实时处理移动人员，能安全绕行时继续；
6. 通道完全阻塞时停车等待并周期性重新规划，不强行穿越；
7. TF、雷达、定位或任务节点异常时由安全仲裁持续归零；
8. 返回起点后发布完成状态并保持零速度。

## 验证门槛

测试必须按以下顺序逐级通过，不跨级：

1. 纯 Python 单元测试：安全超时、状态转换、航点顺序和失败处理；
2. 无底盘输出的 ROS 接口测试；
3. 架空车轮验证速度路由、限速和超时归零；
4. 空场低速单目标导航；
5. 固定障碍物局部绕行；
6. 人员从路径侧面和正面进入时的减速、停车与恢复；
7. 完整 `起点 -> 1 -> 2 -> 3 -> 起点` 重复运行；
8. SSH 断开、任务节点退出、雷达丢失和 TF 中断等故障注入。

每次落地测试都要有现场人员靠近电源控制，并保留无需网络即可断电的手段。

## 网络与协作记录

上午使用手机热点 DHCP 时，小车地址从 `192.168.49.8` 变为
`192.168.49.25`，开发机地址也发生变化。地址变化发生在无线链路重新接入或
热点重新分配租约之后，不能把某个 IP 写死为长期配置。通过热点已连接设备或
开发机邻居表发现当前地址后再连接。

RViz2 应运行在有图形桌面的开发机，而不是普通 SSH 终端中的 RDK 板端。两端需在
同一网络并统一使用 `ROS_DOMAIN_ID=99`；板端只负责启动传感器和 SLAM 节点。

曾观察到多个 SSH/VS Code Remote 会话并存，旧地址上的连接卡住。该现象与
DHCP 地址变化和残留远程会话一致，但没有 UART 日志证明发生了新的内核崩溃，
不得把它直接归因于既有 AIC8800 内核缺陷。仍禁止重启 NetworkManager、
`wpa_supplicant` 或热点服务。当天上午结束时机器人已断电充电。

队友代码必须进入各自的 Git 分支或 worktree，不能继续只保存在
`/home/sunrise`，也不能多人在同一工作树中切换分支。
