# 系统架构

## 设计目标

三个 Demo 独立启动。算法节点不直接访问串口或相机设备；厂商驱动负责转换为标准 ROS 消息，便于替换驱动和离线测试。任务二采用小车厂家导航，任务三使用独立的颜色分类控制链，两套运动控制不得同时启动。

```text
MS200P ──> 雷达驱动 ──> SLAM / 定位 / 动态避障 ─┐
IMX219 ──> 相机驱动 ──> 颜色与柱体感知 ───────┤
编码器/IMU ──────────> 里程计与状态估计 ──────┼─> Demo 行为节点
                                                    │
Demo 速度请求 ──> 安全仲裁（超时/急停/限速） ────┴─> 底盘驱动
```

任务三运行时，`rdx_sorting_safety` 是分类推动速度命令的唯一出口。它接收
`/rdx_sorting/cmd_vel_request` 并向厂家底盘使用的 `/cmd_vel` 输出限速、超时和急停处理后的
命令。任务二运行厂家导航时不启动任务三节点。底盘接口、坐标系和话题名称必须以实机检查
为准，不能依据产品宣传页猜测。

## 计划模块

| 模块 | 责任 |
| --- | --- |
| Bringup | 启动厂商驱动、静态 TF 和硬件配置 |
| Base control | 8 字轨迹、速度约束和停止行为 |
| Vendor navigation | 任务二建图、地图定位、规划与动态避障；比赛默认使用厂家方案 |
| `rdx_color_sorting` perception | IMX219 图像解码、HSV 三色分类、瓶形检测和可选雷达关联 |
| `rdx_color_sorting` behavior | 搜索、目标选择、叉形结构对准、推动、释放和返回状态机 |
| `rdx_sorting_safety` | 任务三限速、命令超时、急停、输出冲突和可选雷达停车 |

ROS 包名统一使用 `rdx_` 前缀。只有跨包确有需要时才创建自定义消息；优先复用 `geometry_msgs`、`nav_msgs`、`sensor_msgs` 和标准动作接口。

## 坐标与配置

任务二沿用厂家导航的坐标系。任务三默认从启动时的 `/odom_raw` 原点定义三个相对分类区域，
不要求地图；可选地图返回模式保留但默认关闭。最终帧名以实机 TF 为准。速度、距离阈值、
颜色阈值、场地边界和堆放策略必须通过 YAML 参数配置，禁止写死在节点代码中。

仓库中的 `rdx_navigation`、`rdx_mission` 与 `rdx_safety` 是早期自研任务二方案，暂时保留作
实验记录和参考，不属于当前比赛默认架构。
